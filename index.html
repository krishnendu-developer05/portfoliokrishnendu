PROTOTYPE SYNTHETIC DATA

MuleShield

follow the money. find the mule.

Problem: mule accounts hide suspicious money transfers inside ordinary-looking transaction graphs.

My role: founder / project lead — product concept, risk logic design, and interface. Implementation is AI-assisted, disclosed openly.

Prototype scope

  • Graph-based analysis of account relationships & transaction patterns
  • Risk indicators and an investigator-oriented interface
  • Risk-gated payment workflow — as a product concept

Honesty note — hackathon prototype. The live demo uses illustrative data; no real bank or government integration, no real money flow. Documented backend / ML / graph technologies describe the intended architecture, not a completed stack.

CH 04

The Process

Spec before code. Always.

spec.mddraft → verified
  1. ✓ understand the problem — who hurts, how much
  2. ✓ define requirements — the contract, written down
  3. ✓ product spec — scope, edge cases, non-goals
  4. ✓ architecture & data model — before the first commit
  5. ✓ component system — designed, then built
  6. ◐ AI-assisted implementation — research, build, debug
  7. ◐ human verification — I check everything it claims
  8. ○ iterate → working product → version two

AI is a tool in my process — not the process.

I work spec-first: the problem, the requirements, the architecture, the data model — written and thought through before implementation begins. AI tools accelerate research, implementation, and debugging inside that spec.

What stays human: problem framing, product decisions, verification, and learning. The machine drafts; I am responsible for what ships. This portfolio itself was built under the same discipline.
